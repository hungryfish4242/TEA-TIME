## Proposed delivery and visual direction

Implement M1 first and leave bun/tart visibly locked until M2 sign-off. Use a cream order-slip background, deep green typography, red stamps, clear numbered chapters and original CSS/SVG food placeholders. These visual decisions are proposed by the implementer, not yet approved by the user. Keep English UI and exact development disclosures from the spec. Large controls and a compact counter/table composition must work at 375 × 667 and 1024 × 768.

The supplied specification already chooses a static implementation. A framework would conflict with that decision; implementing M1 and M2 together would bypass the specified M1 review gate. This plan follows the existing static/M1 approach.

## Global constraints

- Hash routes: `#/`, `#/order`, `#/tea`, `#/bun`, `#/tart`, `#/scene`, `#/certificate`.
- `?mode=kiosk` enables kiosk behavior; `?dev=1` exposes development completion controls; `?mock=fail` exercises timeout fallback; `?reset=1` requests staff reset confirmation.
- No framework, runtime external resources, live AI, historical development copy or dependency installation.
- Exact badge: `DEV BUILD — not for visitors`. Audio remains disabled with `Narration not in this build.`
- Preserve all four `ccttm.*.v1` storage keys and schemaVersion 1. Names remain in memory; transcripts use sessionStorage; event buffers never contain raw questions or names.
- Development content carries `devOnly: true` and `DEV-` sources. Production validation must reject it.
- At least 44 × 44 CSS px controls, keyboard access, focus management, reduced motion, text labels and sufficient contrast.
- M1 is local and internal. M2, live AI, reviewed cultural content, narration and final art are separate later work.

## Contract decisions and discrepancies

- Build-now orders interaction before Q&A and stores one chapter per JSON file; use those M1 contracts over the PRD's earlier sequence and combined content file.
- M1 topic tags are `craft`, `ratio`, `origin`, as specified in build-now; the PRD's `tea_craft` example does not replace this development contract. Future live integration must normalize validated tags at the adapter boundary.
- Visitor/kiosk reset keeps settings; staff reset clears them, following build-now section 4.4. The broad reset wording in its completion checklist is interpreted as staff reset.
- `storyBeat` counts completed beats. The existing chapter status distinguishes the fresh intro from the first story beat; reloading an in-progress chapter resumes its derived step. Do not add a parallel persisted screen field.
- Retry timing is configurable; proposed wider good window is ±350 ms (first attempt ±250 ms). This value is an implementation choice because the spec only says wider.
- Preserve last completed pour and good-pour count using the fields explicitly allowed by build-now section 4.3. Do not introduce a storage migration.
- Keep an explicit production flag in config; production startup rejects development content or a mock adapter even if someone hides the badge.

## Review focus

1. Corrupt or inaccessible storage: continue with valid fresh/in-memory state and explanatory help text; exercise in task 1.
2. Rapid clicks, route changes and reloads: no duplicate cards/events or late Q&A writes into a new visit; exercise in tasks 1, 3 and 4.
3. Unknown content tags, invalid answers and markup strings: reject invalid schemas and render answer text safely; exercise in tasks 2 and 4.
4. Certificate names with markup, emoji or maximum length: safe display, valid PNG, no persisted name; exercise in task 5.
5. Kiosk countdown cancellation, focus restoration and reduced motion: retain a usable journey; exercise in task 6.
